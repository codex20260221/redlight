# Issue-driven development roadmap

Reviewed the open issue descriptions and every available comment in `michaelmawhinney/redlight` on 2026-10-18 against the local implementation. No issue, pull request, workflow, or release was modified. Local implementation and isolated tests do not establish native/hardware acceptance or close a GitHub issue.

## User priorities and dependencies

| Request | Local implementation and next step |
| --- | --- |
| [#27 Tray visibility](https://github.com/michaelmawhinney/redlight/issues/27) | Previously one fixed tray icon. This checkpoint adds bright monochrome off/Strict/Luma/attention shapes and isolated resource/state/failure tests. Explorer, theme, DPI, and filtered-display acceptance are pending. Existing recovery controls and tray retry safeguards are preserved. |
| [#1 Adjustable red brightness](https://github.com/michaelmawhinney/redlight/issues/1) | Not implemented. Current transforms use full red intensity; Luma presets change channel weights, not brightness. Next meaningful implementation: validated integer 1–100%, default 100% preserving current output, scale only the red coefficients, preserve exact green/blue/black zeros and alpha, and use the existing checked live-change/rollback/original-restoration machinery. Integrate persistence/profile migration, preferences, and usable tray adjustment. Magnification is the initial correctness target. Gamma currently verifies a full-scale red white endpoint; assess driver restrictions and comparison policy separately rather than weakening restoration or claiming parity. The owner's [comment](https://github.com/michaelmawhinney/redlight/issues/1#issuecomment-4401953189) explicitly supports lower red-only output and unchanged 100%. |
| [#17 Optional start with Windows](https://github.com/michaelmawhinney/redlight/issues/17) | Not implemented. No startup entry is installed. Add explicit user-controlled, disabled-by-default per-user integration after brightness. Decide one native mechanism, handle quoted portable paths and executable moves, verify writes/removal, preserve visible errors and retry, and avoid overwriting unrelated entries. Profile import must never silently grant startup consent. Startup should open the tray with filtering off. No real registry/startup testing is authorized. |
| [#3 Gradual transitions](https://github.com/michaelmawhinney/redlight/issues/3) | Not implemented. Revisit after brightness, as the owner's [comment](https://github.com/michaelmawhinney/redlight/issues/3#issuecomment-4401991857) requests. Specify a red-only intensity ramp; ordinary RGB interpolation from the original display would retain green/blue during activation. Restore, exit, environment changes, and recovery must stay immediate. Define cancellation, target edits, timer ownership/failure, and countdown interactions before implementation. |
| [#4 Scheduling](https://github.com/michaelmawhinney/redlight/issues/4) | Countdown auto-restoration (0–240 minutes), warnings, retries, and persistence already exist. Wall-clock activation schedules do not. The owner's [comment](https://github.com/michaelmawhinney/redlight/issues/4#issuecomment-4401992980) calls out persistence/startup/manual controls. Define manual override, sleep/resume and clock/DST changes, missed triggers, startup-off behavior, and precedence over countdown/restoration before implementation. Never re-enable while recovery is pending. |
| [#23 Per-monitor filtering](https://github.com/michaelmawhinney/redlight/issues/23) | Not implemented. Fullscreen Magnification applies one desktop transform; logical desktop diagnostics are not per-monitor control. The [discussion](https://github.com/michaelmawhinney/redlight/issues/23#issuecomment-5518042811) proposes isolated per-monitor magnifier controls, including the planetarium need to leave a projector unfiltered. Treat this as research/prototype only. No production integration or working claim without later authorized validation of isolation, input/cursor, mixed DPI/coordinates, taskbars/video/acceleration, power/hotplug, and performance. Existing MagRedProbe is not such validation and must not be run. |

## Verification boundaries

Brightness and the subsequent priority items above are plans, not implementations started at this checkpoint. Work is limited to local commits, with no pushes, PRs, issue edits, releases, GitHub Actions, or execution/testing of RedLight itself. Static analysis, builds, isolated fake-API code tests, and static package inspection are the permitted verification scope. Manual/native qualification is listed in [release validation](release-validation.md); current development stop/resume instructions are kept in the root development handoff.
