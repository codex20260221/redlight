# Issue-driven development roadmap

Reviewed the open issue descriptions and every available comment in `michaelmawhinney/redlight` on 2026-10-18 against the local implementation. No issue, pull request, workflow, or release was modified. Local implementation and isolated tests do not establish native/hardware acceptance or close a GitHub issue.

The owner's [comment](https://github.com/michaelmawhinney/redlight/issues/4#issuecomment-4401992980) requests more real-world backend experience, which isolated tests cannot establish. Never re-enable while recovery is pending. |
| [#23 Per-monitor filtering](https://github.com/michaelmawhinney/redlight/issues/23) | Not implemented. Fullscreen Magnification applies one desktop transform; logical desktop diagnostics are not per-monitor control. The [discussion](https://github.com/michaelmawhinney/redlight/issues/23#issuecomment-5518042811) proposes isolated per-monitor magnifier controls, including the planetarium need to leave a projector unfiltered. Treat this as research/prototype only. No production integration or working claim without later authorized validation of isolation, input/cursor, mixed DPI/coordinates, taskbars/video/acceleration, power/hotplug, and performance. ## Verification boundaries

Brightness, optional startup, and activation-only fade-in are implemented locally; schedules and per-monitor research remain subsequent priorities, with dependencies described above. Work is limited to local commits, with no pushes, PRs, issue edits, releases, GitHub Actions, or execution/testing of RedLight itself. Static analysis, builds, isolated fake-API code tests, and static package inspection are the permitted verification scope. Manual/native qualification is listed in [release validation](release-validation.md); current development stop/resume instructions are kept in the root development handoff.
