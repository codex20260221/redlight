# Per-monitor research (issue #23)

Production per-monitor filtering is **not implemented or qualified**. This research follows the [issue](https://github.com/michaelmawhinney/redlight/issues/23), the [planetarium/projector use case](https://github.com/michaelmawhinney/redlight/issues/23#issuecomment-5310658055), and the [proposed control-based probe](https://github.com/michaelmawhinney/redlight/issues/23#issuecomment-5518042811). No RedLight, MagRedProbe, native display experiment, or hardware test was run. Production backend selection, restoration ownership, manifest, and output remain unchanged.

## What the APIs establish

The current fullscreen transform affects the desktop; a windowed magnifier instead renders a captured source area into a host window. This is a possible **opaque transformed copy**, not a translucent red tint and not a proven per-output color pipeline. Microsoft's [Magnification overview](https://learn.microsoft.com/en-us/windows/win32/winauto/magapi/magapi-intro) describes layered hosts, full opacity, transparent mouse handling, 1:1 magnification, cursor options, and the WOW64 limitation. It does not qualify this arrangement for RedLight's projector isolation requirement.

| Area | Documented mechanism and remaining work |
| --- | --- |
| Per-control color | [MagSetColorEffect](https://learn.microsoft.com/en-us/windows/win32/api/magnification/nf-magnification-magsetcoloreffect) / [MagGetColorEffect](https://learn.microsoft.com/en-us/windows/win32/api/magnification/nf-magnification-maggetcoloreffect) set/read a control's matrix and require WDDM. Check both calls and red-only comparison before showing a host. This read-back still does not measure physical output. |
| Source | [MagSetWindowSource](https://learn.microsoft.com/en-us/windows/win32/api/magnification/nf-magnification-magsetwindowsource) uses desktop coordinates. A proposed 1:1 source rectangle must exactly match the destination monitor rectangle, including negative origins, and be revalidated after topology changes. |
| Capture recursion | [MagSetWindowFilterList](https://learn.microsoft.com/en-us/windows/win32/api/magnification/nf-magnification-magsetwindowfilterlist) supports exclusion; inclusion is unsupported on Windows 7+. A control excludes itself automatically. A multi-host probe should explicitly exclude every probe host from every control and verify the list; do not assume one control's self-exclusion prevents cross-control capture. |
| Input | [MagSetInputTransform](https://learn.microsoft.com/en-us/windows/win32/api/magnification/nf-magnification-magsetinputtransform) requires UIAccess, and its documentation includes mouse routing from Windows 10 version 1703. This needs reconciliation with the overview's transparent-host advice, especially for identical 1:1 rectangles. Do not claim click/touch/pen/keyboard passthrough from window styles alone. |
| DPI | [Process DPI awareness](https://learn.microsoft.com/en-us/windows/win32/hidpi/setting-the-default-dpi-awareness-for-a-process) changes coordinate behavior and must be selected before HWND creation. A future separate x64 probe should declare its own reviewed PerMonitorV2 manifest; the current app has no DPI-awareness declaration and remains `asInvoker`, `uiAccess=false`. Do not change the application's privilege or DPI model as a research shortcut. |

Cursor behavior is independently unresolved. The [overview](https://learn.microsoft.com/en-us/windows/win32/winauto/magapi/magapi-intro) distinguishes the ordinary cursor from a control's magnified cursor. The first probe must leave global cursor visibility and input transformation untouched, then measure any colored cursor leakage/duplication. If strict red-only cursor behavior requires global changes, review their ownership/restoration separately before extending scope.

## Geometry and selection preconditions

Use full monitor bounds, not work-area bounds: taskbars must not become uncovered color strips. [MONITORINFO](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-monitorinfo) expresses monitor rectangles in virtual-screen coordinates, which may be negative. An independent native adapter must confirm a consistent pixel coordinate space; a rectangle supplied to a pure planner cannot prove DPI correctness.

Treat all-monitor filtering as the existing fullscreen path. A subset experiment must require a checked, current topology snapshot with unique transient region keys and separate display sources, exact source/destination rectangles, positive representable window dimensions, no overlapping regions, and no RedLight fullscreen/gamma restoration ownership. No monitor enumeration or mapping is added to production in this research.

Windows distinguishes [clone and extended topologies](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ne-wingdi-displayconfig_topology_id). **Inference:** a captured desktop region cannot independently recolor two physical targets that clone the same source image. Reject shared-source/clone/unknown topology for a subset experiment. Nonoverlapping rectangles alone are not proof of independent physical outputs; the native adapter must also establish source/target relationships. Do not persist enumeration order or raw HMONITOR values as monitor identities. Review durable device/path identity and unplug/replacement consent before any user-facing selection preference.

The code-only `experiments/MonitorPlan.h` preflights supplied geometry into caller-owned storage. It describes one exact source/destination pair per selected region and binds it to a topology revision. It rejects invalid/ambiguous input and insufficient capacity before publishing any partial plan. Eight isolated scenarios cover its bounds, gates, publication, and allocation/native-call isolation; the original checkpoint had 464 suite scenarios; the current integrated suite has 542. It does not enumerate monitors, create windows, initialize Magnification, set colors/gamma/cursor/input, or establish that a plan can be displayed correctly.

## Hidden-control preparation component

`experiments/WindowedRedControl.cpp` is a small research component, not a runnable probe or production backend. It borrows a hidden, correctly sized host and owns one hidden child plus its successful Magnification runtime reference. Geometry preflight admits one selected region in a supplied distinct-source pixel-coordinate subset. The caller must establish live topology/DPI/ownership; booleans supplied to this component cannot prove those facts.

The child is created without WS_VISIBLE or magnified-cursor styling. Checked color, all-host exclusion, identity spatial transform, and full source setup precede read-back. [MagSetColorEffect](https://learn.microsoft.com/en-us/windows/win32/api/magnification/nf-magnification-magsetcoloreffect) / [MagGetColorEffect](https://learn.microsoft.com/en-us/windows/win32/api/magnification/nf-magnification-maggetcoloreffect) confirmation uses the existing exact-zero red-only comparison for both modes, every preset, and 1–100% brightness. A failed setter remains failure even if it applied its value. [Exclusion retrieval](https://learn.microsoft.com/en-us/windows/win32/api/magnification/nf-magnification-maggetwindowfilterlist) checks count then complete unique membership/mode in bounded storage; list order is irrelevant. Source coordinates and identity spatial coefficients must match, and hidden host/client geometry is checked again before confirmation. The child's own visible-style bit is checked because [IsWindowVisible](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-iswindowvisible) also depends on ancestor visibility. No undocumented GetLastError value is reported as a Magnification failure cause.

Any failure or nested cancellation keeps `prepared()` false and attempts child destruction before runtime release. Failed destruction retains the exact child/runtime; failed uninitialization retains only runtime ownership. New preparation is blocked until explicit cleanup succeeds. A cleanup guard prevents parent notifications from recursively destroying or releasing resources twice. Primary preparation and cleanup stages remain separate for the frontend to report. A destructor retries best effort and diagnoses incomplete cleanup; the caller must retain the object and borrowed host for retry instead of relying on destruction after failure.

The component neither shows hosts/children nor changes fullscreen matrices, gamma, input transforms, or global cursor visibility. It does not validate host opacity, actual pixel coordinates, clone topology, input routing, lifetime controls, or physical monitor isolation. A future probe must establish these, bind the read-only topology adapter below to explicit consent and a PerMonitorV2 manifest, keep hosts alive, handle environment changes, and add a checked deadline/manual recovery loop before showing anything. Parent destruction/handle reuse outside the ownership contract is not supported. The hidden-control component has no standalone UI, manifest, timer, or monitor enumeration; the separate read-only adapter below now supplies experimental mapping.

The optional native target produces a static library only; it is Off by default and excluded from packaging:

```powershell
cmake -S . -B build-windowed -A x64 -DBUILD_TESTING=OFF -DREDLIGHT_BUILD_WINDOWED_CONTROL=ON -DCMAKE_CXX_FLAGS=/analyze
cmake --build build-windowed --config Release --target RedLightWindowedControl
```

Fifteen isolated scenarios compile the actual component against fake Windows/Magnification functions in `RedLightWindowedControlCodeTests`, linked only to KERNEL32.dll. They exercise all 600 mode/preset/brightness combinations, invalid plans/options, hidden/full/client bounds, exact exclusion capacity and malformed/read-changing lists, every native setup failure, failed-but-applied/ignored writes, unsafe/nonfinite color/spatial data, exact source mismatch, separate cleanup failures and retry, nested cancellation at every preparation API, post-read visibility/geometry changes, cleanup reentry, object-lifetime limits, and allocation/global-API/extended-error isolation. The current full suite has 542 passing scenarios. Native SDK compilation and MSVC analysis pass; neither native control nor application behavior was executed. Show/hide/host lifecycle, opacity, input, and actual hardware acceptance remain unproven.

## Read-only topology adapter

`experiments/WindowedTopology.cpp` now supplies a separate read-only mapping for the isolated frontend. It requires the current thread to compare equal to PMv2 through [AreDpiAwarenessContextsEqual](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-aredpiawarenesscontextsequal), without changing DPI awareness. It queries active, virtual-mode-aware CCD paths through [QueryDisplayConfig](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-querydisplayconfig), handling legacy mode indices and the documented [virtual source-index union](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ns-wingdi-displayconfig_path_source_info) separately. Each source mode must match its adapter/source identity and have positive representable full bounds. Shared sources, duplicate targets/identities, unavailable targets, invalid modes/rotations, and unknown path flags are refused.

[DisplayConfigGetDeviceInfo](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-displayconfiggetdeviceinfo) supplies bounded source GDI names and target device paths. Complete source rectangles must agree with full monitor rectangles and unique names from [EnumDisplayMonitors](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-enumdisplaymonitors) / [GetMonitorInfoW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getmonitorinfow). Work areas are not used. The adapter requires one primary monitor and no overlapping rectangles. Canonical ordering uses adapter/source identity, so enumeration-order changes do not alter the snapshot. Transient region keys and copied device paths are not persisted preferences or a guarantee of durable physical identity.

Two complete semantic captures must agree, including source/target IDs, target device paths, GDI names, bounds, rotation, and primary state. Native padding, unused name tails, and work-area differences are ignored. Fixed capacity is eight outputs/32 mode records; excess estimates are refused rather than truncated. [Buffer-size races](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getdisplayconfigbuffersizes) allow at most three size/query attempts per capture. Direct CCD error statuses are retained. BOOL-only enumeration/monitor-info failures expose their stage without inventing a GetLastError cause. No snapshot is published on any failure.

The completed double capture is accepted only within 2000 ms; this is an acceptance bound, not an interruption/timeout of synchronous Windows calls. Matching captures do not lock topology or exclude an intervening change away and back. A future probe must compare the complete reviewed snapshot again immediately before display, invalidate consent on environment changes, and hide/cancel before potentially blocking recovery reads. Reported source independence cannot prove physical projector isolation, panel output, cursor, or input behavior. Hardware cloning outside Windows and external color tools remain outside this evidence.

The adapter is included only in the optional research static library and its fourth fake-API test executable, `RedLightWindowedTopologyCodeTests`. Thirteen isolated scenarios cover real native request fields, legacy/virtual indices, canonical order, portrait/negative origins/multiple adapters/signed bounds, one/eight outputs, exact Unicode name capacities, unavailable/changed DPI, direct errors, bounded buffer races, malformed counts/paths/modes/names/callbacks, shared sources/duplicate targets, missing/overlapping/mismatching monitors, primary constraints, semantic replacement/layout changes versus ignored data, latency/wrap, and allocation isolation. The current full suite has 542 passing scenarios behind KERNEL32-only import gates. Native SDK/MSVC analysis pass. No real query, display test, or production integration has occurred. The separate frontend below is built/static-reviewed only and must not be run under current restrictions.

## Operator-controlled frontend (built, never run)

`experiments/WindowedProbe.cpp` now provides the separate `WindowedRedProbe` executable. It is **Off by default**, never installed/packaged, and never registered as a CTest test. Current authorization permits compiling/static inspection and isolated fake tests only; it does not permit launching the frontend, including its help/invalid-argument paths. Production RedLight, its manifest, backend selection, preferences, tray, and restoration owners are unchanged.

Arguments are data: `--monitor N` and `--seconds S` are required, with N from 1–8 in the reviewed canonical snapshot and S from 1–30. Optional mode, Luma preset, and whole 1–100% brightness reuse current red-only meanings; defaults are Luma/Classic/100%. There is no implicit activation from empty/help/malformed arguments. Every valid run displays a complete native review with Yes/No defaulting to No, including all snapshot entries, the selected source bounds, current mode/brightness/duration, stop behavior, and unqualified input/cursor/output limits. No profile, startup, or saved preference changes occur.

The frontend holds the same-session RedLight startup guard through review and acquires the cooperating Gamma ownership lease only after explicit Yes, before creating the hidden copy. Existing same-session owners, busy Gamma ownership, and abandoned Gamma ownership are refused without resetting or adopting any display original. The runtime library belongs to the child component. Existing fullscreen color and magnification state must read as identity before visibility; those are read-only checks, not saved-state restoration or proof that other color pipelines are neutral. The probe never calls a global color/gamma/cursor/input setter. External tools do not share these exclusion guarantees.

Recovery controls are positioned and checked on an unselected monitor; moving them, hiding either owned top-level window, session/power/display/settings/DPI changes, normal close, or the stop hotkey requests cancellation. The native panel's initial controlled DPI relocation is the only placement exception, before a capture host exists. Hosts are created hidden with a black background. [Layered-window properties](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features#layered-windows) are set to alpha 255 with no color key, then [read back](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getlayeredwindowattributes); geometry and styles are checked again before and after reveal. The already-confirmed child is shown under the hidden parent before the host. [SetWindowPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos) is checked by its success result plus visibility/style checks, rather than treating ShowWindow's previous-visibility return as success. The panel stays outside the source; moving it cancels rather than retargeting.

Before reveal, topology must still match the complete reviewed snapshot, the current session must be confirmed active/unlocked, and mandatory session notification, Ctrl+Alt+Shift+F12 stop registration, and a checked 100-ms timer must exist. Final topology/session/property confirmation is accepted only within 2000 ms. The 1–30 second monotonic deadline starts before reveal. This is a best-effort timer, not a hard limit on synchronous Windows calls, scheduler stalls, or process suspension. No blocking topology polling runs while the copy is visible.

`WindowedProbeSession.h` coordinates one reviewed run. Cancellation during a native setup/reveal call is retained until it returns and cannot publish or restart the run. A failed-but-partially-applied reveal is unconfirmed. Cleanup attempts hiding first, destroys the owned child/runtime before its host, and retains failed ownership and recovery controls for retry. After the copy is gone, hook/hotkey/lease/timer cleanup cannot recreate it. Stale timer callbacks and repeated stop requests after completion do no native work. A surviving controller remains available after incomplete cleanup/ordinary quit; missing controls/forced Windows termination remain best effort. Callback access is revoked before member destruction. Parent destruction outside the component ownership contract and physical behavior remain unqualified.

Permitted build/static commands (none launch the probe):

```powershell

cmake --build build-windowed --config Release --target WindowedRedProbe
```

The static verifier checks the distinct probe identity, x64 GUI image, ASLR/DEP, normal-user/UIAccess=false privileges, its own PerMonitorV2 declaration, and reviewed Windows imports. It rejects the RedLight application as the probe. Native compilation/MSVC analysis and static resource inspection passed. Thirteen new isolated parser/coordinator scenarios bring the suite to 542: all supported argument ranges/options, malformed/missing/duplicate data, gate/visibility order, every failed setup/reveal, cancellation at each step, exact/wrapped deadlines, expiry inside a show call with/without timer delivery, ambiguous reveal plus failed cleanup, cleanup-only and stale-callback isolation, reentry, and C++ allocation faults. Those tests fake the coordinator's specific resource API; child/topology/shared timer/session helpers have their separate fake-native coverage. **Native frontend Win32 message, mutex, opacity, hotkey, and UI glue was compiled/static-reviewed only, not executed or validated by those coordinator fakes.** Actual panel layout, input/cursor behavior, driver first-frame output, projector isolation, native API failures/retries, and environment/termination behavior remain pending explicit Windows/hardware qualification.

## Probe boundaries and remaining qualification

Keep the native probe separate from RedLight, disabled in the default build and excluded from the portable package. Build/static/fake checks are allowed; running it requires later explicit authorization for display/hardware validation. A successful build or fake API must never be called monitor-isolation validation.

1. Start only with explicit selected output and bounded duration after operator review of live topology. Refuse unknown/clone geometry, an existing RedLight owner, or unsafe privilege/DPI prerequisites. Never reset another tool's fullscreen matrix or gamma ramp to obtain eligibility.
2. Create hosts hidden. Configure checked opacity, 1:1 transform, source, exclusions, and strict red-only color/read-back before any becomes visible. Initially use one selected monitor; add multiple controls only after independent exclusion/input/cleanup review. Do not show a white/unfiltered intermediate host.
3. Keep manual close/recovery and a checked bounded timer. On Escape/close/failure/topology/DPI/suspend/session change, hide/destroy owned hosts immediately; do not retarget them to a replacement monitor. Check removal/destruction/runtime cleanup, retaining handles and controls after recoverable failures. A hidden host is not proof its native resources were released.
4. Do not touch global fullscreen/gamma/cursor/input state in the first probe. Local control teardown should remove only the experimental copy. If runtime initialization/teardown is ambiguous, track ownership separately from completed readiness as in the existing Magnification audit. Never add runtime backend switching to production on the strength of this experiment.
5. External display tools may transform the source, destination, or unselected outputs independently. Do not adopt their matrix as a new RedLight original or promise untouched physical projector output based solely on per-control read-back.

## Evidence required before production consideration

Code-only preflight tests: negative origins, portrait/rotated rectangles, gaps/edge-touching layouts, full bounds, single/multiple selected regions, all/none selection, malformed/duplicate/overlapping/shared-source input, arithmetic limits, stale revision, retained global recovery gate, bounded publication, and allocation/native-call isolation. These tests establish only planning properties.

Later fake-native tests: every create/configure/set/get/show/hide/destroy/timer/runtime failure, partial application and cleanup ownership, all-host exclusion lists, zero green/blue/black offsets across Strict/Luma/brightness, immediate teardown on cancellation/topology/session change, and no global writes. The existing MagRedProbe only exercises fullscreen effects; it provides no evidence for windowed controls.

Manual Windows work remains pending: prove the projector is unchanged while a selected monitor is strictly red-only, check black/white/primaries and cursor, cross-monitor windows and menus, mouse/keyboard/touch/pen and secure/elevated windows, mixed DPI/rotation/negative origins, taskbars/fullscreen/video/acceleration/HDR, source/exclusion feedback, frame latency/performance, hotplug/sleep/lock/session/Explorer recovery, forced termination, and original global state after every cleanup path. Until those results exist, do not expose a production per-monitor selector or claim the feature works.
